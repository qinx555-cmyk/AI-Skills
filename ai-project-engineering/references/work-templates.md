# 工作模板

模板是填充提示，不是每次必须生成的文档。优先沿用项目格式，去掉与任务无关的字段；所有代码路径必须核实。

## 开发/修复任务约定

```markdown
# <任务主题>
状态：拟议 / 已确认 / 实施中 / 已验证 / 阻塞
目标：<具体用户行为或故障>
当前行为 → 期望行为：<可观察差异>
定位依据：<复现、日志、入口、调用链或契约>
涉及模块与文件：<已核实路径及职责>
范围外事项：<仅列容易误解的边界>
关键约束：<现有接口、数据、兼容、失败处理要求>
方案：<必要的实现单元及顺序>
验收：<操作/输入 → 预期结果 → 验证方式>
待决问题：<会影响正确性的用户选择；没有则省略>
```

微型示例：用户说“导出坏了”，先确定是无法触发、服务失败、空文件还是内容错误。定位导出入口与失败日志后，才判断应改界面、业务层还是文件生成逻辑；不要直接重写导出模块。

## 项目入口与模块地图

若已有索引，将条目并入；没有且任务需要时，再建立一个简短入口。

```markdown
# 项目导航
当前架构/约束：<真实文档链接>
开发与验证入口：<从项目配置核实的命令或文档>

| 模块/业务词 | 职责 | 实现入口 | 接口/依赖 | 当前说明/历史决定 |
|---|---|---|---|---|
| <模块> | <做什么> | <真实路径或符号> | <调用方向> | <有效文档链接> |
```

明确箭头含义，例如“A 调用 B”，不要用箭头把文件夹排序冒充已验证的依赖关系。不统计行数作为质量指标。

## 完成记录与后续复查

```markdown
# <任务> 完成记录
目标与结果：<是否达到验收行为>
实际改动：<路径、职责、行为变化>
关键决定：<选择及理由；必要时写放弃方案>
验证证据：<实际运行的命令/操作、结果、覆盖范围>
未验证/未解决：<明确限制>
相关方案与索引：<链接>
```

若后续出现问题，用原验收场景、当前复现结果和最终差异共同复查。旧文档用于找线索，不能单凭“记录写着已完成”判断故障不存在。

## 长任务交接

```markdown
当前目标与已授权范围：...
有效入口/决定：...
已完成并验证：...
进行中与未验证：...
已知问题/未决选择：...
下一步及相关文件：...
```

不要在每轮回复复制全部历史，也不要把本机绝对路径固化成其他项目的默认路径。

## 调用示例

- `使用 $ai-project-engineering 开发以下功能：……先确认当前模块与验收场景，按本项目约定执行。`
- `使用 $ai-project-engineering 排查这个反复出现的错误：……请先复现、查日志与历史修复记录。`
- `使用 $ai-project-engineering 为当前项目建立最小的项目记忆入口，复用现有文档，不修改业务代码。`
- `使用 $ai-project-engineering 接续上次任务，核实交接记录和当前代码状态后继续。`

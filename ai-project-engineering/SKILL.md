# AI 项目工程化开发

把每次任务组织成可追溯闭环：**定位上下文 → 核对目标与边界 → 实施 → 验证 → 更新记忆**。重点是让下一次开发能找到正确依据，而不是增加文档数量。

## 选择工作深度

- **轻量修改**：单点、职责明确且不改变接口或数据契约时，读相关代码和测试，简述目标与验证方式后按已有授权执行；复用现有记录，不强制新建方案、索引或架构文档。
- **持续迭代**：涉及多模块、新能力、复杂故障或多次对话时，使用下述完整闭环；利用现有文档体系承载结果。
- **初始化项目记忆**：用户要求建立项目工作流，或当前任务确实因缺少导航而难以进行时，再补最小入口和模块地图。不要因调用 Skill 自动整理全仓或改写项目规则。

遵守当前项目和会话的确认约定；已有授权继续有效。本 Skill 不额外增加逐步审批，也不授权部署、数据迁移或其他外部操作。

## 1. 先定位，再扩大检索

1. 读取适用的项目说明和 `AGENTS.md`，确认工作目录、现有改动、技术栈及可用验证入口。
2. 从现有文档索引或架构地图查找业务词、模块职责、相关决策及历史修复。沿“索引 → 相关文档 → 实现入口 → 调用方/契约 → 测试”定位。
3. 核实文档引用的路径、符号及行为是否仍存在。历史文档是背景证据；过期方案不能覆盖当前需求。发现文档与代码矛盾时，分别说明“实际行为”和“期望行为”，不要自动认定任一方正确。
4. 没有可靠索引时，以 `rg --files` 和定向搜索定位；证据不足再逐步扩展到相邻模块或全仓。不要把整个代码库与历史文档都塞进上下文。
5. 故障任务先收集复现条件、错误和相关日志，追踪实际调用链后确定修改位置。不要仅凭模块名字猜测根因。

形成足以开始工作的上下文：目标模块、真实入口、相关契约、有效历史决定、仍待核实的信息。未找到的路径应写“待定位”，不能伪造。

## 2. 把需求转成可检查的约定

编码前用简明语言核对：

- **目标行为**：谁在什么条件下做什么，目前怎样，完成后应怎样。
- **范围与依据**：涉及的模块、预期修改位置，以及为什么应由这里负责。
- **验收场景**：可观察的输入、操作与预期结果；包括与本次改动相关的失败或边界情况。
- **约束**：必须保留的行为、数据/接口契约，以及本次明确不做的事项。
- **关键不确定性**：哪些误解会改变方案；能从项目查明的先查，确实需要用户选择的再问。

复杂任务把这些内容写入既有方案体系；必要时使用 [工作模板](references/work-templates.md)。将口语化要求改写为可检查的行为，保留原本意图，不能自行补入用户未要求的功能。

## 3. 将架构术语落到实际边界

不要只写“高内聚、低耦合、单向依赖”。说明：

- 哪个模块拥有业务规则和状态，哪个只负责展示、编排或适配。
- 哪些调用允许发生，通过什么现有接口传递数据；哪些依赖会跨越现有职责边界。
- 是否必须兼容旧接口/数据，失败如何暴露，是否允许回退及其触发条件。

遵循项目现有架构；不因视频案例而强制采用某种语言、框架或六边形架构。兼容和回退是需求决策，不能统一禁止，也不能擅自增加。确需回退时避免吞掉错误或把失败伪装成成功。

如果方案指向与用户目标无关的模块，先核实调用关系。若真正的根因位于共享模块，解释证据与影响，不机械限制在用户猜测的文件中。

## 4. 按可验证单元实施

- 每个单元完成一个可观察行为，保留清晰的改动范围；拆分应有助于验证，不要求任意固定步数。
- 只在与当前目标有关的地方调整结构。重复修补、循环依赖、同一规则多处实现、改一处频繁破坏另一处，可作为局部重构的证据。
- 重构先明确保持不变的行为，再整理职责/接口；范围明显超出已授权任务时单独提出，不自动全仓重写。
- 实施中出现与方案不同的事实，及时更正方案和假设；不要为了让旧方案成立而掩盖现状。

## 5. 用行为证据验收

- 根据实际改动选择验证：相关测试、类型检查、构建、接口请求或真实界面操作。通过与变更有关的必要检查后，避免无依据地反复扩大测试。
- 检查最终差异是否对应目标模块、是否偷偷增加范围，以及相关接口与调用方是否仍一致。
- 区分“代码已写”“检查通过”“运行验证通过”“已部署”。动画、截图、模拟数据或演示页面只能证明其实际覆盖的内容。
- 发现失败时回到复现与证据定位，不用反复泛化重写替代诊断。
- 未能运行的验证注明原因和剩余风险，不声称完成了未执行的检查。

## 6. 更新最小且有效的项目记忆

复用现有记录，仅保留下一次任务有用的信息：目标、关键决定及理由、实际改动位置、验证结果、未解决问题。

- 索引保存“模块/主题 → 当前入口 → 一句话用途”，详细过程放在被链接文档中。已有 `AGENTS.md` 只需要简短导航时，增补相应链接并保留原有规则，不塞入全部历史记录。
- 如果确需新建文档而项目无命名约定，可采用日期、模块、主题组合的名称；这只是可选约定。
- 架构或路径改变时同步相关导航；过期文档标明被替代关系。不要自动删除历史文件。
- 记录“计划”和“已完成”的区别。续接时说明已完成、待完成、已知问题及下一步入口。

结束时简要报告：完成了什么、验证证据、相关记录路径，以及还需用户决定的事项。
